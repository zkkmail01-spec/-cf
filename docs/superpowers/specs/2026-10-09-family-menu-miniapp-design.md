# 家庭点菜微信小程序设计规格

## 1. 项目目标

开发一款仅供家庭内部使用、需要联网的原生微信小程序。家庭成员可以按日期为早餐、午餐和晚餐点菜；厨师长负责维护菜品、分类、食材及家庭成员邀请；系统长期保存每天每餐的菜单记录。

首版成功标准：家庭成员无需学习复杂操作即可完成点菜，厨师长可以独立维护家庭菜谱，并且不同家庭的数据严格隔离。

## 2. 产品范围

### 2.1 首版包含

- 微信身份登录与首次进入引导。
- 创建家庭、通过微信分享加入家庭。
- 厨师长和普通成员两种角色。
- 菜品分类、菜品、图片及食材用量管理。
- 按日期和早餐、午餐、晚餐点菜。
- 记录每道菜的点菜人和点菜时间。
- 按月历及日期查看历史菜单。
- 将历史菜单再次加入指定餐次。
- 根据菜单汇总采购食材并支持勾选。

### 2.2 首版不包含

- 复杂库存、价格、营养和热量管理。
- 支付、外卖、公开社区或菜谱市场。
- 独立手机号账号体系。
- H5、支付宝小程序或原生 App。
- 多家庭同时切换；首版每位用户只加入一个家庭。

## 3. 技术架构

采用原生微信小程序、Python FastAPI 与微信云开发云托管：

- 小程序端负责页面展示、交互状态和非敏感校验。
- 小程序通过 `wx.cloud.callContainer` 调用云托管中的 FastAPI 服务。
- FastAPI 负责微信身份识别、家庭邀请、角色鉴权和全部业务写入。
- SQLAlchemy 2 负责数据访问；开发环境使用 SQLite，正式云托管环境使用 PostgreSQL。
- 微信云存储保存菜品图片，Python 服务只保存云文件标识及元数据。
- FastAPI 以 Docker 容器部署到微信云开发云托管，并暴露 `/api/v1` HTTP 接口。
- 微信 `openid` 作为用户身份依据。生产环境只接受云托管可信身份头；本地开发使用明确启用的模拟身份，不在客户端信任用户自行提交的身份字段。

所有家庭业务表必须带 `family_id`。FastAPI 依赖项根据当前微信身份查询成员关系，再判断是否允许读取或写入目标家庭数据。数据库连接、模拟身份开关和云环境配置通过环境变量注入，不写入源码。

## 4. 信息架构

底部导航固定为四项：

1. 首页：今日菜单、我要点菜、菜谱管理、采购食材、邀请家人和常吃菜推荐。
2. 菜谱：分类浏览、搜索、菜品详情，以及厨师长专属的菜品与分类管理。
3. 记录：月历、日期详情、三餐菜单和再次点菜。
4. 我的：家庭成员、邀请、家庭资料、个人信息、角色和退出家庭。

采购清单属于首页能力，不单独占用底部导航位置。

## 5. 页面与核心流程

### 5.1 初次进入

用户完成微信授权后，系统查询其家庭成员关系：

- 未加入家庭且无邀请参数：显示“创建家庭”和“通过邀请加入”。
- 携带有效邀请参数：展示家庭名称与邀请者，用户确认后加入。
- 已加入家庭：直接进入首页。

### 5.2 点菜

用户从首页进入“我要点菜”，选择日期和餐次，再按分类或搜索浏览菜品。点击菜品卡片可添加或取消，最后提交当次变更。系统保留菜品快照、点菜人和点菜时间。

同一餐可由多位成员持续追加。重复选择同一道菜不会产生重复菜单项，而是在该菜单项中合并点菜人信息。取消操作仅移除当前用户自己的选择；当没有任何成员继续选择该菜品时，才从当餐菜单中移除。

### 5.3 菜品管理

厨师长在菜谱页新增或编辑菜品，包括：菜名、图片、分类、说明和食材列表。每项食材包含名称、数量、单位和可选备注。普通成员只能浏览菜品与食材信息。

删除菜品需要二次确认。删除后菜品不再出现在可选菜谱中，但历史菜单保留已保存的菜名、图片和分类快照。

### 5.4 历史记录

记录页默认显示月历，并标记存在菜单的日期。进入日期详情后，按早餐、午餐和晚餐展示菜品及点菜人。用户可以选择“再次点这桌菜”，再指定目标日期和餐次。

### 5.5 邀请成员

厨师长生成带邀请码的微信分享卡片。邀请记录包含家庭、创建者、有效期、状态和使用限制。受邀用户打开分享后完成微信身份确认，查看家庭名称，再主动确认加入。过期、失效、重复使用或用户已有家庭时，系统显示明确结果并阻止错误加入。

### 5.6 采购清单

系统根据选择日期范围内的菜单汇总菜品食材。相同名称和单位的食材合并数量；不同单位不自动换算。用户可勾选已采购项目，勾选状态按家庭和日期范围保存。首版不管理库存和价格。

## 6. 数据模型

关系型数据库使用 UUID 主键、蛇形字段名和 UTC 时间戳。API 层将字段转换为小程序使用的驼峰 JSON。

### 6.1 `families`

- `id`
- `name`
- `owner_openid`
- `avatar_file_id`
- `created_at`
- `updated_at`

### 6.2 `family_members`

- `id`
- `family_id`
- `openid`
- `nickname`
- `avatar_url`
- `role`: `chef` 或 `member`
- `joined_at`
- `status`: `active` 或 `left`

`family_id + openid` 建立唯一约束；一个 `openid` 同时只能存在一条 `active` 成员关系。

### 6.3 `dish_categories`

- `id`
- `family_id`
- `name`
- `sort_order`
- `is_active`
- `created_at`
- `updated_at`

### 6.4 `dishes` 与 `dish_ingredients`

`dishes`：

- `id`
- `family_id`
- `category_id`
- `name`
- `image_file_id`
- `description`
- `is_active`
- `created_by`
- `created_at`
- `updated_at`

`dish_ingredients`：

- `id`
- `dish_id`
- `name`
- `quantity`: Decimal
- `unit`
- `note`
- `sort_order`

食材单独建表，方便 PostgreSQL 聚合采购清单，并避免依赖特定数据库的 JSON 查询能力。

### 6.5 `meal_orders`、`meal_order_items` 与 `meal_item_selectors`

`meal_orders`：

- `id`
- `family_id`
- `meal_date`: Date
- `meal_type`: `breakfast`、`lunch` 或 `dinner`
- `version`
- `created_at`
- `updated_at`

`family_id + meal_date + meal_type` 建立唯一约束。

`meal_order_items` 保存 `dish_id` 以及菜名、图片、分类和食材 JSON 快照，确保菜品后续修改或停用不会改变历史记录。

`meal_item_selectors` 保存菜单项、选择者 `openid`、昵称和选择时间；`meal_order_item_id + openid` 建立唯一约束。

### 6.6 `invitations`

- `id`
- `family_id`
- `created_by`
- `code_hash`
- `expires_at`
- `max_uses`
- `used_count`
- `status`: `active`、`revoked` 或 `expired`
- `created_at`

邀请链接只携带不可直接推导家庭信息的随机码，数据库保存其 SHA-256 散列值。

### 6.7 `shopping_checks`

- `id`
- `family_id`
- `range_start`
- `range_end`
- `checked_keys`: JSON 数组
- `updated_by`
- `updated_at`

## 7. 权限规则

### 7.1 厨师长

- 创建和修改家庭资料。
- 新增、编辑、停用分类与菜品。
- 维护食材列表。
- 创建、撤销邀请并查看家庭成员。
- 移除普通家庭成员。
- 拥有普通成员的全部点菜和查看能力。

### 7.2 普通成员

- 浏览家庭菜谱和菜品详情。
- 为任意允许日期的三餐添加或取消自己的菜品选择。
- 查看本家庭历史菜单、采购清单和成员列表。
- 修改自己的昵称和头像。
- 主动退出家庭。

所有写操作由 FastAPI 依赖项和服务层二次校验调用者身份、家庭归属和角色。客户端隐藏按钮仅用于改善体验，不作为权限边界。

## 8. 视觉与交互规范

首页采用已确认的“家庭工具箱型”：今日菜单卡片置顶，下方提供点菜、菜谱、采购和邀请等快捷入口，再展示常吃菜品。

- 主色为森林绿，辅色为暖橙，背景为米白。
- 使用大圆角卡片和轻阴影营造家庭厨房氛围。
- 正文不小于 `28rpx`，主要按钮高度不小于 `88rpx`。
- 图标配合文字，不依赖单独图标传达关键含义。
- 早餐、午餐、晚餐使用顶部标签切换。
- 菜品卡片展示图片、名称、分类和选中状态。
- 删除菜品、移除成员和退出家庭必须二次确认。
- 页面适配微信字体缩放、全面屏安全区和常见手机尺寸。

## 9. 并发与一致性

多人同时点菜时，客户端只提交本次增量操作，不上传整份菜单覆盖服务端数据。FastAPI 服务在数据库事务中锁定目标 `meal_orders`，按 `version` 合并选择者，再递增版本号。PostgreSQL 使用行锁保证写入顺序；SQLite 开发环境通过乐观版本检查模拟冲突。发生冲突时自动重试有限次数；仍失败则返回 HTTP 409 和可重试提示。

菜品管理采用软删除，即设置 `isActive = false`。历史记录完全依赖菜单项快照，不因菜品后续修改或停用而变化。

## 10. 异常与状态设计

- 网络中断：保留尚未提交的界面选择，显示重试入口。
- 空菜谱或空分类：显示引导文案；厨师长可直接新增，普通成员可联系厨师长。
- 图片上传失败：保留文字表单数据，允许单独重试图片。
- 邀请无效：区分过期、撤销、次数用尽、已加入家庭和家庭不存在。
- 无历史记录：展示空状态和“去点菜”入口。
- 权限变化：FastAPI 返回 HTTP 403 时刷新成员身份，并提示当前角色已变化。
- 提交成功：使用微信原生轻提示并返回最新云端结果。

## 11. 测试与验收

### 11.1 Python API 测试

- 未登录、非家庭成员和跨家庭请求必须失败。
- 普通成员调用厨师长管理接口必须失败。
- 重复加入家庭、过期邀请和超出使用次数必须失败。
- 同一菜品被多人选择时正确合并选择者。
- 多人并发点菜不丢失数据。
- 停用菜品后历史快照仍可读取。

### 11.2 页面与流程测试

- 创建家庭、邀请加入、退出家庭形成完整闭环。
- 厨师长可完成分类、菜品、图片和食材维护。
- 成员可为指定日期和餐次添加或取消菜品。
- 月历和日期详情准确显示三餐记录与点菜人。
- 再次点菜可复制到目标日期和餐次。
- 采购清单可正确汇总同名同单位食材。
- 空状态、加载状态、错误状态和重试流程完整。
- 常见 iPhone 和 Android 微信窗口尺寸下无内容遮挡。

### 11.3 交付边界

代码交付包含微信小程序源码、FastAPI 源码、Dockerfile、数据库迁移、云托管部署说明、云存储配置说明和基础演示数据。由于当前没有用户的微信 AppID、云环境 ID和云托管服务名，项目默认使用占位配置及本地模拟身份；用户在微信开发者工具中填入实际配置并开通云开发云托管后即可进行真实联网验证。
